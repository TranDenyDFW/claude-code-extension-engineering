One row per mechanism pairing, compressed to a single line so a combination can be checked without opening both references first. Owner, failure path and regression test stay as a terse per-pairing checklist rather than expanded prose, because baseline testing showed a model generates that guidance unaided; the reason this file exists at all is the part it cannot generate, which is the version gates and config filenames.

| Skill + Subagent vs Workflow + Subagent vs Agent Team | the three ways to delegate, and the axis is WHO owns the control flow. Skill + Subagent: the MODEL owns it, advisory routing, cheapest, correct for one bounded job whose result returns to the caller. Workflow + Subagent: the SCRIPT owns it, deterministic loops and fan-out, 1000 per run and `min(16, available CPUs - 2)` concurrent rather than a flat 16, no filesystem API inside the script and no Date.now(), correct when the orchestration itself must not drift; stable since 2.1.154. Agent Team: NO ONE owns it centrally, peers message each other, experimental and env-gated behind CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS, one team per session with no nesting, cost multiplies per teammate, correct only when peers must challenge each other's findings mid-flight. Failure paths differ the same way: a mis-routed skill produces a plausible wrong answer, a workflow null-fills the failed item, a team stalls holding a task. Regression test = the same fan-out task through all three, asserting the workflow alone gives identical run-to-run structure. |

| Hook vs Monitor vs Channel | the disambiguator, and the axis is where the event ORIGINATES and WHO CAN REFUSE IT. A hook's event originates INSIDE the harness lifecycle and the hook can refuse it; a monitor's originates in an outside process the plugin itself started and NOTHING can refuse it, because no deny contract exists anywhere in its schema; a channel's originates OFF the machine and the only thing that can refuse it is application code you wrote. trigger = a lifecycle event, a stdout line, an inbound notification, respectively; instruction owner = the hook wiring, the monitor command, the channel server's instructions string; executor = the hook handler, the monitor process, the model reading the delivered tag; enforcement point = hook exit code, then none, then none; external dependency = none, the watched source, the remote platform and the org policy; package boundary = a hook stands alone or ships in a plugin, a monitor is plugin-only, a channel needs an MCP entry plus a launch flag plus an allowlist; version gate = the hook event on the target build, plugin monitors at 2.1.105, channels at 2.1.80; failure path = all three are INDISTINGUISHABLE FROM SUCCESS at a glance, since a crashed hook looks like a deliberate block, a dead monitor looks like a quiet system, and a disabled channel looks like a quiet platform; regression test = feed each a known-bad input and watch it go red, meaning a call the hook must deny, a killed monitor process with the workflow still completing in silence, and a channel run with channelsEnabled off while curl still returns 200. |
| Permission rule + Hook | trigger = the same tool call reaches both, and the deny rule is evaluated FIRST; instruction owner = settings.json for the rule, the handler for anything conditional; executor = the harness for the rule, a spawned process for the hook; enforcement point = BOTH, and they fail in opposite directions, since the rule holds when the handler is deleted or crashing while the hook can carry a condition the rule cannot express; external dependency = the handler's interpreter, which is the hook half's most common failure on Windows; package boundary = both are settings plus one script, so a plugin ships them together or the hook half dangles; version gate = Edit-and-Read-only path-rule consultation requires 2.1.210, and on an older build a Write(path) rule is inert AND silent; failure path = the hook fails OPEN and the rule keeps holding, so the pair degrades to rule-only rather than to nothing, which is the right way round; regression test = delete the handler and assert the rule still denies, then add an allow rule for the same path and assert deny still wins. |
| Permission rule + Sandbox | trigger = a Bash command, which both see, and a built-in file tool call, which only the rule sees; instruction owner = settings.json for both, but different scopes: the rule is project-scoped, the enforce-the-sandbox keys are documented for MANAGED settings; executor = the harness for the rule, the operating system for the sandbox; enforcement point = both, and the coverage sets are complementary rather than nested, since the rule reaches the built-in file tools and a by-example subset of Bash while the sandbox reaches all of Bash INCLUDING child processes and none of the built-in tools; external dependency = Seatbelt on macOS, two packages on Linux and WSL2, and NOTHING on native Windows because the sandbox does not run there; package boundary = a repo can ship the deny rule and cannot usefully ship the sandbox half, which belongs to an administrator; version gate = strictAllowlist at 2.1.219, and the sandbox is absent on native Windows at every version; failure path = by default an unavailable sandbox WARNS and runs unsandboxed, and failIfUnavailable: true turns that into a refusal to start, which on Windows means every developer on the team is blocked; regression test = a subprocess write to the protected path, which must succeed with the rule alone and fail with the sandbox on, plus a built-in Edit, which must fail with the rule alone and succeed with the sandbox alone. |
| CLAUDE.md + Permission rule | trigger = every session for the prose, the matching tool call for the rule; instruction owner = split, and the split is the POINT rather than the defect here: the rule refuses, the prose explains why and what to do instead; executor = the model for the prose, the harness for the rule; enforcement point = the rule only, and the prose is worth having precisely because a bare denial is opaque; external dependency = none; package boundary = CLAUDE.md is project-local, and the rule lives in .claude/settings.json beside it; version gate = none for the prose, 2.1.210 for the path-rule consultation semantics; failure path = the two DRIFT, so the prose describes a protection the rule no longer implements, or names a path the glob does not cover, and nothing detects it because neither half validates the other; regression test = assert the denial fires for a path the prose names, which is the only mechanical link between them. |
| CLAUDE.md vs Hook vs permission rule vs sandbox | the enforcement disambiguator, and the axis is COVERAGE SET, not strength. There is no ordering here where each layer contains the one below: every one of the four has a gap another one fills, so "use the strongest" is not a well-formed instruction. CLAUDE.md covers the model's INTENT, everywhere, and refuses nothing; a PreToolUse hook covers exactly the tools its matcher names and FAILS OPEN on a missing, crashing or wrong-interpreter handler, so a Write-or-Edit matcher never sees a Bash command; a permissions deny rule is harness-owned and survives handler deletion, covers the built-in file tools plus a Bash subset the docs give BY EXAMPLE and never enumerate, and leaks at the subprocess boundary where a Node or Python script opens the file itself; the OS sandbox closes exactly that boundary for Bash and its children, covers NONE of the built-in file tools, and DOES NOT RUN ON NATIVE WINDOWS. trigger = every session, a lifecycle event, a tool call, a Bash command, respectively; enforcement point = none, hook exit code, rule match, the operating system; failure path = ignored, fails open, leaks at the subprocess boundary, unavailable on Windows; version gate = none, the hook event on the target build, 2.1.210 for path-rule consultation, absent on Windows at every version; regression test = for each layer, the vector the OTHER three cannot see, which for the rule means a subprocess write and for the sandbox means a built-in Edit. Two measured additions the documentation does not give you: the recognised-Bash sentence names Bash and never PowerShell, and a PowerShell Add-Content wrote through a live Edit(...) deny rule on 2.1.220; and a project-scope permissions.allow entry granted nothing for an interpreter command in a -p session while --allowedTools did, so approval and denial are separate gates that a benchmark must not conflate. |
- COMMAND + HOOK: a command file whose whole job is to trigger the hook that does the work. Instruction owner is the hook; the command is a thin entry point that exists so the capability has a name a user can type.
