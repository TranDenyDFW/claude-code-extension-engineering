## Issues found

1. `tools/packs/validate-before-action.mjs:1103` is an assertion that cannot fail, and it is
   guarding the exact property the surrounding block is named after.

   ```js
   check('it is NOT named settings.json', !Object.keys(files).includes('permissions.json')
     && !/^settings\.json$/.test('permissions-deny.json.proposal'));
   ```

   The second conjunct tests a STRING LITERAL against a regex. No code in this repository can
   change its value; I evaluated it directly and it is `true`. The first conjunct looks for the key
   `permissions.json`, which `buildBundle` (lines 774 to 781) never produces: the only keys it can
   emit are `README.md`, `conformance.json`, `settings.json`, `.claude/hooks/validate.mjs` and
   `permissions-deny.json.proposal`.

   Reproduced: I added `files['settings.json'] = denyProposal(policy, a.denyCandidates);` beside
   line 780, so every deny-bearing bundle's `settings.json` became the non-loadable proposal
   document. `node tools/packs/validate-before-action.mjs --self-test` still exited 0 and still
   printed `ok   it is NOT named settings.json`, together with `ok   it exists for a static-shape
   deny rule`, `ok   the wiring uses ${CLAUDE_PROJECT_DIR}, never the bare form` and
   `ok   V1 files are frozen`. The entire self-test was blind to it. Reverted with
   `git checkout --`, confirmed the added line is gone.

   Blast radius: the `--gate` DOES catch this one (I ran it under the mutation: exit 1,
   `GATE FAIL: 3 probe(s) diverged`, V1, V2 and V6 red). So the shipped behaviour is protected. What
   is wrong is the self-test's claimed coverage: a reader of that row believes the file naming is
   checked, and it is not checked at all.

2. `--prove-fail` and `validate-before-action` disagree about `fail-posture` and `wiring`, and the
   repository's own hollowness detector says so.

   `tools/extension-prove.mjs:1240-1288` states the contract: "Every `enforce` case in every bundle
   is run against two controls ... An `enforce` case that still PASSES against either is asserting
   nothing about the extension", and line 1255 includes kinds `enforce`, `wiring` and
   `fail-posture` deliberately (line 1254: "fail-posture is INCLUDED. Excluding it left the
   mutation engine ungated.").

   I ran that detector against the six bundles the CLI generated in check 26:

   ```
   node tools/extension-prove.mjs --prove-fail --bundles tmp/rv
   ```

   Exit 1. `prove-fail: 68 enforce/wiring/fail-posture case-runs against empty and inert controls`
   then `PROVER IS HOLLOW` with 27 survivor rows. Every one of the six bundles emits at least
   these two cases whose PASS does not depend on the generated extension at all:

   - `matcher-scopes-to-the-declared-tool`, kind `wiring`, `expect: { fired: 0 }`
     (`validate-before-action.mjs:637-641`). Zero handlers fired is precisely what an EMPTY
     settings.json produces.
   - `crashing-handler-fails-open`, kind `fail-posture`, `expect: { decision: { not: 'deny' } }`
     (line 646-649). Passes against both the empty and the inert control.
   - Plus, on the inert control, the `-permits-*` wiring cases
     (`approved-npm-permits-1/2`, `tests-must-pass-permits-when-met`,
     `prod-gates-permits-when-met`, `manifest-must-be-valid-permits-valid-document`).

   The prove-bench fixtures write fail-posture the other way round, `"expect": {"decision": {"not":
   "allow"}}` (verified in `tests/prove-bench/fixtures/correct-guard/conformance.json:96-102`),
   which does go red against both controls. And `extension-scaffold.mjs:490-500` records that this
   exact lesson was already learned for `protect-path`: "`tamper` replaced `fail-posture` here ...
   the case was byte-identical to the enforce case above it: a check that could not fail,
   presenting as the strongest assertion in the spec." The new pack reintroduced the shape in a
   different form.

   These cases are counted in each bundle's headline (`8 case(s): 8 passed`) and in the gate's "all
   green, frozen kinds match", so they inflate the evidence. Nothing in CI runs `--prove-fail`
   against generated bundles, so it is invisible today.

3. `tools/extension-scaffold.mjs:401-409`, the injection labelled `validate-before-action: an
   invalid policy is accepted instead of refused`, does not test policy validation.

   Its own comment says "The defect: skip validation and trust the policy. Reproduced by handing
   analyse a policy with a rule that declares no reason and an unanchored pattern, which the real
   validator refuses." The code does neither. It calls the REAL `V.analyse(i)`, which runs
   `validatePolicy` and throws `PolicyRefusal` on anything invalid, and only then flips
   `defaultDecision` and every rule's `decision` to `allow`. Replacing `validatePolicy` with a stub
   that always returns `{ok: true}` would not redden this row.

   It is also a near-duplicate of the injection immediately above it at lines 378-381 (`a deny
   decision is flipped to allow`), which flips the same rule decisions. So of the 11 `MUST FAIL:`
   rows check 21 counts, two exercise the same seam, and the seam the row is NAMED after
   (`policy-schema.mjs` refusing an invalid policy) has no injection guarding it.

4. The CLI prints a false final line whenever a strict spec is NOT DONE.

   Observed in check 26 (`block-recursive-delete-absolute`) and check 27. The prover correctly
   emits `8 case(s): 8 passed, 0 failed.`, then `NOT DONE: the requirement is ABSOLUTE and a
   residual vector survives.`, then the paragraph explaining that every case passing IS the point.
   `extension-scaffold.mjs:162-165` then prints:

   ```
   NOT DONE: the generated bundle does not satisfy its own conformance spec.
   ```

   which is false: the bundle does satisfy its spec. `reportCode` (`extension-prove.mjs:812-815`)
   returns 1 both when a case failed and when a strict residual survived, and `scaffold()` reads
   only the exit code, so it cannot tell them apart. This directly contradicts the design note at
   `extension-prove.mjs:792-804`: "reported separately from a failing case so the two are never
   confused."

5. `tools/packs/index.mjs:120-121` has a conjunct that is true by construction.

   ```js
   check('--list reports a summary and required inputs for each',
     listPacks().every((p) => p.summary.length > 30 && Array.isArray(p.requires)));
   ```

   `listPacks()` builds each row as `requires: p.requires || []` (line 56), so
   `Array.isArray(p.requires)` is always true. Only the summary-length half can fail. The row's
   name promises that required inputs are reported; that half asserts nothing.

6. `tools/extension-prove.mjs:1134-1138` degrades silently in the wrong direction.

   ```js
   check('a CALIBRATED denied shape decides deny',
     !RECOGNIZED_WRITE_SHAPES.get('append-redirect') || B("printf 'x' >> infra/main.tf").decision === 'deny');
   ```

   Both keys exist today (I read them out of `tools/bash-recognition.mjs`: `append-redirect`
   `{denied:true,n:10,passes:10,cli:"2.1.224 (Claude Code)"}` and `opaque-subprocess`
   `{denied:false,n:10,...}`), so both rows are live right now. But if a calibration key is renamed
   or dropped, the guard makes the row PASS vacuously instead of failing. The enclosing
   `if (RECOGNIZED_WRITE_SHAPES.size)` has an explicit else-branch that says so out loud; the
   per-key guard does not.

7. `tools/packs/validate-before-action.mjs:917-935` (`checkProbe`) never asserts that the generated
   `settings.json` wires anything.

   Its only settings.json assertion is negative: complain IF the bare `$CLAUDE_PROJECT_DIR` form is

   `permissions.deny` against a frozen array by value, and which asserts every key of its sandbox

and neither is caught by any numbered check in the spec. Issue 3 additionally means one of the 11
