## 9. Blinding

**(a) Can a grader packet contain the arm that produced a sheet?**
Not as a label. `pack()` builds each sheet as `{ sheet: N }` plus the seven graded fields plus
an optional `citations` object, and never copies an arm name in. The arm mapping is written
only to `tests/tier3/blinding-map.json`, which no grader reads. `blindingProblems()` then
re-checks the serialized packet for the literal markers `"arm"`, `"b"`, `"bplus"`, `"d"`,
`arm_<x>` and `arm-<x>`, and independently checks that every scenario carries exactly three
sheets and that no sheet carries an unexpected key.

Caveat, and it is a real one: this proves no arm **label** survives. It does not prove the arm
is unrecoverable. See what-the-spec-missed item 1, where I show the arm is in fact recoverable
with 100% accuracy from the live packets.

**(b) Rotation or permutation?**
Permutation. `PERMUTATIONS` is a literal table of all six orderings of three items, indexed by
`FNV-1a(id) % 6`. The file states explicitly that a rotation was rejected because it preserves
relative order and could be inverted.

**(c) How many distinct orderings can the mechanism produce?**
Six, the full symmetric group on three sheets.

**Measured over all 60 real scenario ids** (my own script, importing `permutationFor` and
`ARMS` from the tool):


## 13. Is B+ a fair control for arm D?

Judgement, in my own words.

**B+ has not been handed any of the skill's specific decision content.** I read step 1 of both
files side by side. Arm D's step 1 names two concrete artifacts and tells the agent to work
them in order: `references/selection.md` for the decision axes, and
`references/composition-cards.md` for the mechanism pairing when a need spans two mechanisms.
Arm B+'s step 1 says only "Work mechanism selection systematically rather than reaching for the
first mechanism that fits", and to do it "from reasoning". No axis is named. No composition
pairing is named. No taxonomy, no ordering of criteria, no list of what to consider. The only
thing B+ inherits is the *instruction to be systematic*, which is the procedural variable that
B+ exists to hold constant, not decision content.

The Resource sections are consistent with this: B+ is told explicitly it does not have the
repository and must not reason from memory of it.

So on the specific question asked: **B+ has not been contaminated with the skill's decision
content. PASS.**

On whether it is a *good* control, my honest read is that it is well constructed but leans
weak, and it leans weak in the direction that flatters arm D. "Be systematic" without a named
system is close to an empty instruction; a model given it will invent its own decision
procedure, and the quality of that invention is uncontrolled and will vary per scenario and per
agent. Arm D gets a fixed, named, ordered procedure. So the D versus B+ gap conflates two
things: the *content* of the skill's axes, and the mere fact of having *any* stable named
procedure at all. If D beats B+, the attribution string the scorer emits ("The skill's decision
content carried it") is stronger than the design can support, because a placebo reference
containing arbitrary but stably named axes was never run.

That is a design limit, not a defect, and it is the standard limit of an active control. It
does not contaminate the control and it does not confound the D versus B comparison that drives
the headline verdict. I would want it stated as a caveat next to the attribution sentence.

One asymmetry I do not think is a fairness problem but should be named: B+ is given a false
premise ("you do NOT have access to the repository") that D is not given. Both arms run in this
repository. Enforcement of that instruction is by the model, not the harness, and nothing in
the harness detects an arm B or B+ agent that reads the skill anyway. Only the citation rate
detector exists, and it detects the opposite failure (an arm that stops fetching docs).

**PASS**

Value: **6**. Declared at module scope as a `const` literal, with a comment recording it was
committed 2026-08-02 before any answer agent ran.

The three verdict branches in `verdict(rows)`:

| Condition | Headline |
|---|---|
| `gap >= DECISION_MARGIN` | `SHIP` |
| `gap > 0` | `INCONCLUSIVE` |
| else | `NEGATIVE` |

where `gap = d.overall - b.overall`. There is a fourth early return, `INCOMPLETE`, when arm b
or arm d is absent; that is a guard, not a verdict on the data.

Both the margin and the branch logic are **fixed constants and fixed comparisons written into
the file**. Nothing in `verdict()` reads the data to choose a threshold, and nothing computes
the margin from the score distribution, the sample size or the observed variance. `verdict()`
receives only the scored rows and applies the literal 6.

A separate use of the same literal `DECISION_MARGIN` drives the attribution string, comparing
`d.overall - bplus.overall` against the same 6.

## What the spec missed

### 1. The blinding is defeated for arm B, at 100% accuracy, in the live packets

This is the most serious thing I found and no check asks about it.

`blindingProblems()` explicitly whitelists `citations` as a permitted sheet key
(`tools/tier3-pack.mjs` line 75: `k !== 'sheet' && !GRADED_FIELDS.includes(k) && k !== 'citations'`),
and `pack()` copies it through verbatim (line 107: `if (src.citations) sheet.citations = src.citations;`).

But `arm-b.md` never asks for citations, while `arm-b-plus.md` and `arm-d.md` both do. So arm B
sheets have no `citations` object and the other two always do. The presence or absence of that
one key identifies the baseline arm perfectly.

I proved this on the real benchmark output. In a temp copy I ran `node tools/tier3-pack.mjs`
against the answer files currently in `STAGE\answers` (20 scenarios answered so far, 60 sheets),
then cross-referenced every produced sheet against `blinding-map.json`:

```
Arms: b, bplus, d  packets: 2  scenarios: 20
PASS: no packet carries an arm label, and every scenario has one sheet per arm present.

sheets examined: 60
sheets WITHOUT a non-empty citations object, by true arm: {"b":20,"bplus":0,"d":0}
sheets WITH    a non-empty citations object, by true arm: {"b":0,"bplus":20,"d":20}
RULE "no citations => arm b": precision 20/20, recall 20/20
```

A concrete packet, which passed the blinding gate:

```
scenario S001  true map: {"1":"bplus","2":"d","3":"b"}
  sheet 1  keys=[...,"version_caveat","citations"]  citations=4 urls
  sheet 2  keys=[...,"version_caveat","citations"]  citations=4 urls
  sheet 3  keys=[...,"version_caveat"]              citations=ABSENT
```

Why it matters rather than being cosmetic: the headline verdict is
`gap = d.overall - b.overall`. Arm B is the arm the whole decision rule is measured against,
and it is the arm a grader can pick out of every packet without effort. `grader.md` tells the
grader not to try to work the arm out, and explains that *position* carries no information,
which is true, but it does not warn that the missing citations block does. A grader who notices
knows which sheet is the baseline on all 60 scenarios. That is exactly the bias the permutation
work exists to remove, and the permutation work is otherwise excellent.

`tier3-pack.mjs --self-test` cannot catch this because its fixtures construct all three arms
identically via `mk()`, so every synthetic sheet has the same key set. The defect only appears
against real answers.

Cheap fixes, any one of which would close it: strip `citations` from the packet and score
citation rate from the answer files (which `tier3-score.mjs` already does, via its own
`loadAnswers()` and `citationRates()`, so the packet does not need it at all); or normalize every
sheet to carry a `citations` key, empty for arm B; or add a `blindingProblems` rule that the key
set must be identical across the three sheets of a scenario.

I checked the prose channel too, and it is clean: no arm D sheet mentions `selection.md`,
`composition-cards`, or its decision axes (only one sheet in 60 uses the word axis at all), and
mean prose length does not separate the arms usefully (b 1848 chars, bplus 2299, d 1858). The
structural tell is the whole problem.

### 2. `tier3-pack.mjs --check` can pass vacuously over committed artifacts

`tier3-score.mjs` guards this case deliberately and with a comment: if there are no grades but
`results-tier3.md` already carries a generated block, that is drift and it exits 1
(lines 357 to 366).

`tier3-pack.mjs` has no equivalent guard. Its `--check` path returns before it ever looks at
`blinding-map.json`:

```js
if (!armsPresent.length) {
  console.log('No answer sheets in tests/tier3/answers/ yet. Nothing to pack.');
  process.exit(CHECK_ONLY ? 0 : 1);
}
```

So a committed `blinding-map.json` and committed packets with an empty or missing `answers/`
directory pass the drift gate silently. Proven in a temp copy: I packed the real answers, then
deleted only the answers directory, leaving the map and packets in place:

```
Test-Path blinding-map.json = True
Test-Path answers           = False
No answer sheets in tests/tier3/answers/ yet. Nothing to pack.
--- pack --check with map present but NO answers, exit=0
```

Positive control, so this is a real hole and not a claim that the gate never works. With the
answers present, tampering the map is caught correctly:

```
FAIL: blinding-map.json does not match what the answers and scenario ids derive.
--- tampered map exit=1
PASS: the committed blinding map matches the derived one.
--- restored map exit=0
```

The gate is sound when the inputs are there. It just does not notice that they are gone. This
matters because answer files are large and are exactly the kind of thing that gets gitignored
or pruned, and the moment they are, CI goes green over an unverifiable blinding map. The fix is
one `if` mirroring the one already written in the scorer.

### 3. The completeness gate accepts surplus records addressed to sheets that do not exist

`completenessProblems()` is documented as requiring that every (scenario, sheet, field) appear
exactly once. It enforces that from below only. A record naming a sheet number absent from the
blinding map passes every filter (known scenario, known field, valid score), lands in `seen`
under a key the map loop never visits, and is then silently discarded by `score()` because
`map[g.scenario]?.[String(g.sheet)]` is undefined.

```
baseline problems: 0  records=42
with a record for a NONEXISTENT sheet 4: problems=0  -> []
```

The gate also never compares the total record count against the expected `scenarios x 3 x 7`.
`grader.md` tells the grader to count its records before returning, but the scorer only counts
what is missing, never what is extra.

Severity is lower than items 1 and 2: it cannot corrupt a published number, because the stray
records are dropped rather than scored, and the common real failure (a grader mislabelling
sheet 3 as sheet 4) is still caught, because sheet 3 then goes missing. But a gate whose entire
reason for existing is the S055 short-return would be strictly better with a total-count
assertion, and it is two lines.

### 4. `tests/results-tier3.md` still publishes the two claims these commits were written to retire

`tools/tier3-strip.mjs` opens by stating that the 2026-07-30 run recorded answer agents
receiving a file "verified to contain zero expected-key text", and that "Nothing in the
repository performed or recorded that verification, so the claim rested on a person having
looked." `tools/tier3-pack.mjs` says the same about the rotation claim.

Both claims are still in `tests/results-tier3.md`, unqualified:

- lines 19 to 20 still assert the answer agents "received a keys-stripped scenario file,
  verified to contain zero expected-key text";
- line 29 still says the sheets' "order rotates per scenario id", which is now also
  contradicted by the implementation, since `tier3-pack.mjs` uses a permutation and its header
  explains at length why a rotation was rejected.

The doc describes the older run, so it is not false about that run, but this repository's stated
defect of record is prose drifting from the artifacts it describes, and these are the two
sentences the new tooling exists because of. One qualifying clause on each would close it.

### 5. Smaller observations, no action implied

- `score()` builds a `byScenario` Map (lines 130 to 133) that is written and never read. Dead.
- `completenessProblems()` line 96 has a no-op `.replace(' sheet ', ' sheet ')`, producing
  messages like `S001 sheet 1 sheet primary: graded 2 times`. Cosmetic.
- `verdict()` computes the gap from already-rounded integer percentages, so a true gap of 5.6
  can present as 6 and trip SHIP. Given the margin is explicitly a noise floor rather than a
  significance test this is defensible, but it is a rounding-dependent branch on a
  pre-committed threshold and worth one sentence of disclosure.
- `blindingProblems()` searches for the bare markers `"b"` and `"d"` in the serialized packet.
  These are single letters, and the packet also embeds the full answer key and scenario prose,
  so a graded field whose entire value is the string `b` would false-positive. No occurrence in
  the current data, and the failure direction is safe (over-reporting), so this is a note only.
- The packet embeds the complete answer key for all eight key fields, by design, so the grader
  can score against it. Nothing enforces that a packet file never reaches an answer agent. The
  strip gate protects `batches/`; there is no equivalent guard on `packets/`.
