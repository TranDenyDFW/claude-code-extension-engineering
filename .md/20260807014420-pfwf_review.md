## Issues found

**1. A CHECK THAT CANNOT FAIL, in the new `scoring-hardening rounds` rule, and a false claim about it in IMPROVEMENTS.md.**

`tools/coverage-report.mjs:170` adds `{ label: 'scoring-hardening rounds', live: hardeningRounds, re: /(\w+)\s+rounds of scoring hardening/gi }`. The live value is DERIVED with `HEADING_WORDS` (which knows one through five) but the document side is MATCHED with `WORDS`, whose floor is `six: 6`. So on the matching side any word from one to five becomes `NaN`, hits `if (!Number.isFinite(n) ... ) continue;` at line 198, and is skipped without a word. The live value is 5, which sits inside exactly that blind band.

Observed, in this working tree, restoring after each probe:

- Appending `FOUR rounds of scoring hardening` to `README.md`, that is the literal historical defect string: gate exit `0`, disagree section `none`. (`tmp/v-probeA.txt`)
- Appending `4 rounds of scoring hardening`: gate exit `1`, `scoring-hardening rounds: doc says 4, live is 5`. (`tmp/v-probeB.txt`)
- Appending `seven rounds of scoring hardening`: gate exit `1`, `doc says seven, live is 5`. (`tmp/v-probeC.txt`)

So the rule fires only on digits or on words at or above six. Then the decisive test: I replayed the real pre-fix README through the current gate, `git show 38a3399:README.md > tmp/README.old; cp tmp/README.old README.md; node tools/coverage-report.mjs --doc-numbers`. That README carries `FOUR rounds of scoring hardening` on its line 45. Result: exit `1` with THREE disagreements, `lint-bench fixtures`, `composition cards (table row)`, `hook events (table row)`. The fourth rule stayed silent on the very line it was written for. `README.md` restored, `git diff --quiet HEAD` clean.

Consequence for the claims: `IMPROVEMENTS.md:693` states "Four new facts were added and each was watched reddening against the real stale string BEFORE the README was fixed." That is not true of the fourth. Either it was watched reddening against a digit form rather than the real stale string, or it was not watched at all.

Worse, the rule is currently DORMANT repo-wide. The only two live statements matching its phrasing are `tests/results-lint-bench.md:162` ("## Five rounds of scoring hardening", inside the gated `tests/results*.md` glob) and `docs/RESULTS.md:131` ("Five rounds of scoring hardening", gated). Both say "Five", both parse to `NaN`, both are skipped. The rule compares zero statements today and cannot compare the number it derives. If the count moves from five to six and those two sentences stay at "Five", nothing reddens. This is the same failure shape as the four gates found last round: a green that does not depend on the thing under test.

Minimal fix: use `HEADING_WORDS` on the matching side for THIS rule only (its phrasing "rounds of scoring hardening" is specific enough that "five" cannot be an English quantifier there), or require the published sentences to use digits. Note that the spec's own check 11 only exercises three of the four new rules, which is how this survived to the review.

**2. `quote-check.mjs` normalises hard enough that a meaning-changing upstream edit passes. Demonstrated end to end, not argued.**

The gate is not hollow (check 16 proved it reddens), but its comparator is a whole-page `String.includes` over text with backticks, asterisks, underscores, markdown links and trailing sentence punctuation stripped, plus ellipsis fragments checked independently. I built two copies of the real 187-page mirror under `tmp/`, mutated one page in each, and ran the real tool with `--mirror`:

- Case A, an exception clause appended upstream. `sandboxing.md` line 124 upstream reads `* Explicit [deny rules](/docs/en/permissions) are always respected`, and `references/sandboxing.md:32` quotes it as `"Explicit deny rules are always respected."` I changed upstream to `... are always respected, except for commands the sandbox auto-allows, where the rule is skipped entirely`. Result: `node tools/quote-check.mjs --mirror tmp/fakemirror` exit `0`, `PASS every verbatim quote still appears upstream.` The quoted sentence now means close to the opposite for the case a reader most cares about, and the gate is green. 14 of the 34 live quotes end in punctuation that `trimTail` strips, so 14 are open to exactly this suffix attack.
- Case B, a glob widened upstream. `permissions.md` upstream says ``Use `Bash(rm *)` ... instead.`` I widened it to ``Bash(rm **)``. Result: exit `0`, `PASS`. `normalise()` strips `*`, so `Edit(infra/**)`, `Edit(infra/*)` and `Edit(infra/)` are all one string. Verified directly: `normalise("Edit(infra/**)")` and `normalise("Edit(infra/*)")` both return `"Edit(infra/)"`. Single-star versus double-star is precisely the distinction this project's own README calls out as trap 4, and the gate cannot see it.
- Case C, a short ellipsis fragment is dropped and never compared. `fragmentsOf` filters out fragments under 12 characters. `references/permissions.md:25` is the one live quote with an ellipsis, and its second fragment `"instead."` is silently discarded, so only the first half is ever checked. I confirmed the drop programmatically (`tmp/probe-quote3.mjs` prints `DROPPED FRAGMENT: permissions.md:25`). Nothing warns that part of a quote was not checked.
- Case D, fragments are order-independent and whole-page scoped. `findQuote` requires every fragment to appear somewhere in the SAME page, in any order, in any section. A sentence relocated into a "deprecated, this was never true" block still counts as found (verified with a synthetic page).

The tool's own header and its final NOTE line disclose the general limitation ("proves the sentence exists, NOT that its surrounding context still means the same thing"), which is honest. The reason to report it anyway is that the reference headers written this round lean on this gate as the evidence for "re-verified against 2.1.224", and 101 of 186 upstream pages changed. The class of change most likely in a docs refresh is precisely a hedge or exception appended to an absolute sentence, and that is the class this comparator is blindest to.

Two smaller points in the same file:
- The self-test row `a backticked code span is not a quote` is green by construction. Its input, `- use \`Edit(docs/**)\` here [OFFICIAL]`, contains no double-quoted span at all, so `quotesIn` returns `[]` no matter what the backtick handling does. Delete every backtick rule and the row still passes. **4. The new overwrite guard in `bash-recognition-run.mjs` is untested and fails open.**

It has no self-test row. `--self-test` prints 13 rows, all about verdict attribution and shape composition; none touches the guard (`tmp/v-brr.txt`). For a mechanism whose stated reason for existing is "This repo has already lost two corpora that way", shipping it with no known-bad input is the pattern this repo keeps writing items about.

It also fails open on the case that matters most. Line 328: `if (prior && prior.cli_version && prior.cli_version !== out.cli_version)`. A prior file that fails to parse sets `prior = null` (the `catch` at line 327), and a prior file with no `cli_version` also falls through. Both paths then overwrite the existing record in place. A truncated or half-written record is exactly when you least want the surviving bytes destroyed. Second, when the guard does divert, it writes `dest.replace(/\.json$/, '-<tag>.json')` with no existence check, so a second run on the same non-canonical build silently overwrites the first diverted file.
