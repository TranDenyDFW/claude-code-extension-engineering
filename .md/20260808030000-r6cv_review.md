### On check 12: are the specs now covering the right boundaries

**The main thing is fixed, and I want to say that first without hedging.** The four-round sequence had
a single structural cause, named by round 5: the product's headline sentence is emitted by a process
and every gate tested a function. `tests/cli-contract.mjs` closes that, and I measured it rather than
reading it. Bypassing `finalVerdict` at its call site while leaving the function correct is the exact
mutation that left twenty-three gates green last round; it now leaves three of them green and turns
`node tests/cli-contract.mjs` red, naming two contracts and quoting the forbidden sentence. The gate
is wired into CI in the same commit. The mutation that survived four consecutive fixes cannot survive
a fifth. That is the correct instrument aimed, for the first time, at the boundary where the defect
actually lives, and it is the highest-value thing produced in six rounds.

**Are the remaining findings cosmetic?** Three of the four are. Issue 2 (the `mustNot` guard is
id-coupled) weakens a data-shape assertion whose subject is not the defect: I checked, and the
positive `must` lists alone still catch the four-round falsehood, so the gate's protective power does
not depend on the guard I broke. Issue 3 is a docs line missing a flag. Issue 4 is a claim in a commit
message being stronger than the code behind it. None of the three would let a wrong sentence reach a
user.

**Issue 1 is not cosmetic, and it is not the same class as the four-round defect.** It is a gate that
announces "guarded by NOTHING" and exits 0 in the same breath, reachable by a one-token deletion, for
the third round running. What makes it worth naming is what it says about the fix pattern rather than
its blast radius: the response to "this line is asserted by nothing" was to move the line into a
helper and write a comment saying it now cannot diverge. It can, I did it, and the comment is the only
thing standing where a test should be. The counterpart fix in the same commit, round 5's issue 3, was
done the other way: a self-test row was added, and deleting the line now reddens a named row. One
commit contains both patterns, and only one of them is verifiable.

**The class of defect these specs still structurally cannot reach.** It has moved up one level, and it
is worth stating precisely because it is no longer the same gap. Every must-fail demonstration that
mutates the TOOL and requires a NAMED assertion to redden is still performed by a human reviewer, once,
and then lives only in a review document. Checks 4, 6, 7, 8 and 9 in this spec are all of that shape,
and check 8 is the one that found something. `tests/cli-contract.mjs` proves it can fail when its
EXPECTATIONS are mutated (its own comment is candid that this is the cheap direction), but nothing
automated mutates the CLI's verdict path and requires a contract to go red. The evidence that the new
gate sees round 5's finding 1 is my check 4 and the commit message's word MEASURED. Next time someone
edits `finalVerdict` or its caller, the gate will catch it, so that specific loop is closed by
construction. What is not closed is the general one: for every OTHER load-bearing line the repository
adds, the only thing that will notice its deletion is the next reviewer's hand.

The repository already owns the cure and applies it in exactly two places. `--prove-gate-can-fail`
declares a list of defects, injects each through a seam, re-runs the whole gate and requires it to
redden and then return to green, and it is the single most reliable thing here: eleven injections,
eleven `ok MUST FAIL` rows, plus a baseline row added after a previous review caught it passing
vacuously. `tests/validation-family-breaks.mjs` does the same for handlers. Round 5's recommendation
was to generalise that pattern; this commit did not, and issue 1 is precisely what a
`--prove-can-fail` on `coverage-report.mjs` would have caught mechanically. My answer to check 12 is
therefore narrower than round 5's: the boundary question is settled and settled correctly, and what
remains is that the repository has a proven mechanism for automating must-fail proofs and applies it
to two of its roughly twenty gates.

**1. Round 5's issue 2 is not fixed. It is relocated, one token deep, for the third consecutive

mutation (check 8).**

The commit moved `hits++` from beside the complaint into a `complain` helper and documents the change
as: "The counter cannot be removed from the branch below without the message going with it, because
they are now one call." The counter can be removed. It is a separate statement inside the helper's
body. Deleting `hits++` from `tools/coverage-report.mjs:286` and putting `{ this is not json` into

The reason it survives is unchanged and stated plainly in round 5: `tools/coverage-report.mjs` has no
`--self-test` of any kind (`grep -n "self-test\|selfTest\|SELF-TEST" tools/coverage-report.mjs` returns

healthy tree. So the assertion the commit added is protected by the same nothing that round 4's
version was, and its correctness rests on a manual mutation performed once per review.

Two aggravating details. First, the helper is now shared, so deleting that one token disables the
counter for every future `complain()` caller at once, which is a slightly larger blast radius than the
inline version had. Second, the "one call" property was applied to one of five complaint sites: lines
307, 348, 361 and 364 still do a bare `hits++` next to their own `console.log`, which is exactly the
shape the commit's own comment identifies as one that "silently breaks".

The fix that would end this: `coverage-report.mjs` needs a `--self-test` that feeds it an unreadable
`results.json` and requires exit 1, and the CI step needs to run it. Round 5's issue 3, in the same
commit, was fixed that way and now behaves correctly under check 9.

**2. The `mustNot` guard inside the new self-test is coupled to id spelling, so it does not cover one
of the four verdict contracts and can be voided by a rename. Reproduced by two mutations (check 6).**

`tests/cli-contract.mjs:199-200`:

```js

    CONTRACTS.filter((c) => /says-the-spec-is-satisfied|says-DONE|failing-cases/.test(c.id)).every((c) => c.mustNot.length > 0));
```

Two consequences, both measured. Emptying the `mustNot` of `legacy-prose-path-still-works` (line 81)

This is a weakened assertion, not an open hole: I verified the gate still catches the real defect
without any `mustNot` at all (see issue 4), so nothing about a user-visible sentence is at risk here.
