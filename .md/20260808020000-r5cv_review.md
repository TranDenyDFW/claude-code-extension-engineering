## On check 15: are the specs testing the right things

Short answer: the numbered checks are technically sound and aimed one step behind the defect. The
technique is right and the scope is wrong, and the scope error is the same one every round.

**What the specs do well.** Specs 4 and 5 stopped asking "does the fix work" and started asking
"would anything notice if the fix were removed". Checks 5, 7, 8 and 10 in this spec are all genuine
must-fail demonstrations: each names a line to break and an outcome to require, and all four behaved.
That is the correct instrument, and it is why round 5's numbered section produced no surprises.

**What they keep missing, and it is one thing.** Every round's numbered checks are derived from the
previous round's findings, so they inherit the previous round's model of where the bug lives. They
verify the fix. They never verify the code the fix was written INTO. Both of this round's provable
findings are lines this commit added whose deletion nothing notices: `hits++` in `coverage-report`
(issue 2) and the exit comparison in `recordDiff` (issue 3). Neither is a check the spec asked for,
and neither could have been, because the spec was written from a list of things already believed
broken.

**The specific blind spot, stated concretely.** The specs test FUNCTIONS, and the product's claim is
made by a PROCESS. There is no gate anywhere in this repository that runs the scaffold CLI and asserts
its stdout. Check 6 does exactly that, correctly, and it is a line in a review document, so it
evaporates when this review is filed. That single gap explains the whole four-round sequence: round 2
found the falsehood in a stdout substring match, round 3 in the prover's reporter, round 4 in a branch
inside `scaffold()`, and round 5 in the glue inside `scaffold()`. The bug did not survive because the
logic kept being wrong. It survived because every fix was validated at the function boundary while
the sentence is emitted at the process boundary, and the specs kept validating at the same boundary
the fix was written at.

**What would actually break the cycle**, in order of value:

1. A gate that spawns `tools/extension-scaffold.mjs` on each `examples/policies/*.json` and asserts
   the exact final block, so `scaffold()` stops being unreachable. Issue 1's mutation reddens the
   moment such a gate exists, and so would round 2's, round 3's and round 4's. This is the single
   highest-value check missing from the repository, and no spec has ever asked for it.
2. Generalise `--prove-gate-can-fail` beyond the gate. The repo already owns the right pattern: a
   declared list of load-bearing lines, each deleted in turn, each required to redden a NAMED row.
   It is applied to the scaffold gate and to the prover and to nothing else. Applied to
   `coverage-report`, `recordDiff` and the scaffold CLI, it would have caught issues 1, 2 and 3
   mechanically instead of by a reviewer's hand.
3. A spec-authoring rule: for every assertion a commit adds, require deleting the ASSERTED CODE and
   watching the named row go red. Checks 5, 7, 8 and 10 do this for the four things the previous
   review named. Nothing does it for the twenty-odd other lines the same commit wrote.

**One more thing worth saying.** The check that has found something every single round is the one
that is not numbered. Four rounds of numbered checks have produced zero failures on their own terms;
four rounds of open-ended hunts have produced fourteen issues. That is evidence for spending the
spec's budget on the hunt rather than on the list, and for writing the numbered list to prove the
PREVIOUS fix is reachable rather than to prove it is correct. Correctness has not been the failure
mode in this project even once. Reachability has been the failure mode every time.
