## Issues found

1. **Defect (found independently, outside the spec's checks): a single-file target plus a fail-closed clause produces a bundle that fails its own spec, every time.** Scaffolding `Prevent any edit to \`config/prod.secrets.yaml\`. This must hold even if the handler crashes.` exits **1** with `7 case(s): 5 passed, 2 failed.` and `NOT DONE: the generated bundle does not satisfy its own conformance spec.` Root cause, confirmed by reading the source: `toGlob` correctly leaves a single file alone (line 72, `if (/\.[A-Za-z0-9]+$/.test(t)) return t;`) and the deny rule is correctly emitted as `Edit(config/prod.secrets.yaml)`, but `conformanceFor` unconditionally appends a subtree suffix to build its case paths (lines 113 and 114, `inside = ... + '/main.tf'` and `nested = ... + '/nested/deep/x.tf'`). The generated cases therefore target `config/prod.secrets.yaml/main.tf`, a path the emitted deny rule cannot match. C1, C3 and C5 still pass because the generated hook denies by prefix, but C6 and C7 delete or crash the handler, leaving only the deny rule, which correctly allows a path it was never asked to protect. I isolated the scope: the same single-file target with no fail-closed clause selects the hook mechanism and passes 5 of 5, so the failure is specific to `permission-deny` plus a single-file target. Severity: the tool is honest about it (non-zero exit, `NOT DONE`, no false green), but it writes the bundle directory to disk anyway and there is no wording that reaches a working fail-closed single-file bundle. The self-test does not catch this because its single-file assertion covers `toGlob` only, not `conformanceFor`. Suggested fix: in `conformanceFor`, when the glob contains no `*`, use the target itself as `inside` and skip or re-derive `nested`.

2. **Minor, narrow protection vocabulary.** `PROTECT` (line 52) does not match natural phrasings such as "Never allow modification of X". My first probe with that wording was refused with `UNSUPPORTED: the requirement does not describe protecting a path`. This is the tool's documented refuse-rather-than-force-fit posture and is safe, not wrong, but it will refuse requirements it could in fact handle. Worth noting only because the refusal message says the requirement "does not describe protecting a path" when it plainly does.

3. **Minor, commit attribution is inaccurate.** The verify spec lists `tests/prove-bench/make-fixtures.mjs` as modified in this phase, and the `33bc2db` commit message states "Also fixes a CRLF portability defect in the prove-bench drift gate." `git show 33bc2db --stat` lists only four files and that is not one of them, and `git log -- tests/prove-bench/make-fixtures.mjs` returns only `2ec8786`. The normalisation is real and I verified its behaviour in checks 9 and 10; it simply landed in the previous commit, not this one. No functional impact.
