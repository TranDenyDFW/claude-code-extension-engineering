## Issues found

1. **The `19 user records against 21 tool_result blocks` figure in bullet 196 is not independently reproducible, and my measurements run the other way.** The claim record's note says `The 19 user records against 21 tool_result blocks count was sampled from a live 2.1.219 transcript`, and the same sentence sits at `lib\transcript.mjs:17`, so the bullet is a faithful transcription and check 12 passes on its stated criterion. But that figure requires `tool_result` blocks to OUTNUMBER `type:"user"` records, which needs at least one record carrying two or more `tool_result` blocks. I scanned 250 live transcripts drawn from all 1,154 session files on this machine, including 15 written in the 2026-07-25 to 2026-07-29 authoring window, and found `records carrying more than one tool_result block: 0` and `files where tool_result blocks exceed type:user records: 0`. In every file the two counts were equal or the user count was higher (per-file ratios 0.65 to 1.00; aggregate 1462 blocks against 1904 user records). The mechanism the bullet teaches is correct and I confirmed it strongly; only the specific numeric pairing rests on nothing but the author's own comment. Because `tests/questions.jsonl` row F263 keys its answer on the literal string `19 user records against 21 tool_result blocks`, the suite now pins a number I could not reproduce. Recommend either re-deriving the count and correcting both the bullet and `lib\transcript.mjs:17`, or restating the point without the pair, for example that most `type:"user"` records in a live tail are tool-result carriers, which I measured as 88 user records yielding 7 real user turns in one 42 MB transcript.

2. **Minor, presentational.** Bullet 194 says that without a model-reachable exit, `stop_hook_active` and the 8-block cap `are the only things that ever end the turn`. That holds for a handler with no state of its own, but the reference implementation it is drawn from also ends the turn through its own per-turn state cap (`ask-question-guard.mjs:83-101`, which passes with `turn cap (already blocked this turn)`). Bullet 195 supplies that third mechanism, so the two are coherent read in order; a reader taking 194 alone would slightly overstate the wedge. No change strictly required.

3. **Minor, context.** The mirror's `hooks.md:2367` advises hooks acting on the just-completed turn to use `last_assistant_message` rather than reading `transcript_path`, because the transcript file is not guaranteed to hold the final message at Stop time. Bullet 196 prescribes reading the transcript without noting that. It is not a contradiction, since 196 is about turn-boundary and loop-cap detection, which `last_assistant_message` cannot provide, and the adjacent OFFICIAL bullet at `hooks.md:188` already introduces the field. Worth a clause only if the section is revised for other reasons.

Nothing else. No check failed, no scope creep, no banned dash characters, no lost ledger records.
