# Doc + Creator + Prover: make the extension carry its own falsifiable acceptance test

## Context

`P:\ClaudeExt\Archive\Claude Code Extension Improvement - Docs+.md` proposes building "Arm D",
a hybrid docs-plus-skill workflow, and testing whether it beats docs-alone by 6 points.

**That work is done and the answer is negative.** The rebuilt v2 instrument ran it: docs-alone
versus docs-plus-skill is 20 wins, 20 losses, p=1.000 across 1,680 double-graded cells at 92%
inter-grader agreement. The Docs+ document also contradicts itself: its own section 1 states
"Adding the skill on top of docs (Arm D) yielded 92% ... suggesting no net gain", and its
sections 2 through 8 then propose discovering that. It additionally cites a stale 82% baseline.

So the premise needs replacing, not executing. The null is not a failure of the skill. It is
evidence that **answering architecture questions is saturated** (docs alone reach roughly 90%)
and is therefore the wrong property to optimise.

The user's instinct, "not only documentation but doc + creator", is the right response. This
plan takes it one step further, because a bare creator would be redundant: Anthropic's
`create-plugin` already scaffolds skills, agents, hooks, MCP and settings, and it is already
unpacked on this machine.

**The gap is not generation. It is proof.** Verified by reading the shipped bytes today:

`plugin-dev/skills/hook-development/scripts/test-hook.sh`, lines 245 to 252:

```bash
if [ $exit_code -eq 0 ] || [ $exit_code -eq 2 ]; then
  echo "✅ Test completed successfully"
  exit 0
```

Exit 0 is allow. Exit 2 is deny. **Both print success.** The script takes
`<hook-script> <test-input.json>` and accepts no expected outcome anywhere. A hook written to
block a destructive command, that allows it, passes.

Worse: `grep -i 'hooks\.json|matcher'` over that file returns **nothing**. It pipes stdin
straight into the handler, so the matcher is never evaluated. A hook with `matcher: "Edit"`
whose handler blocks `Write` passes `validate-hook-schema.sh`, passes `test-hook.sh`, and never
fires in production. Nothing in the 99-repo corpus closes that loop.

This is exactly the "a check that cannot fail proves nothing" anti-pattern this repo already
has a house rule and a `--prove-fail` culture around, shipped by the official toolkit.

**Intended outcome:** the creator's deliverable stops being *the extension* and becomes *the
extension plus a conformance spec that can fail*. No project in the surveyed corpus ships that.

---

## What this is NOT

Stated first, because two thirds of the obvious plan is redundant and should not be built.

- **Not a new generator.** `create-plugin` works. We wrap it.
- **Not more documentation.** Our own p=1.000 null says a further knowledge artifact is not
  measurably distinguishable from zero once docs are present. Writing more doc is arguing with
  our own best measurement.
- **Not a skill-trigger evaluator.** `skill-creator/scripts/run_eval.py` already spawns a real
  `claude -p`, watches for an actual `tool_use` of `Skill`, and does a 60/40 stratified split
  with blinded history and precision/recall over 3 passes. It is better than what we would
  write. My earlier claim that "nobody proves a generated skill triggers" was wrong.

---

## The differentiator, stated measurably

> `test-hook.sh` passes a hook that allows what it was asked to block. `extension-prove.mjs`
> fails it. Same hook, same input, one command each.

That is reproducible in two lines and is the entire product claim.

## Phase 1: the prover (the only genuinely new thing)

### New: `tools/extension-prove.mjs`

Conventions match the repo exactly: bare `node tools/x.mjs`, Node stdlib only, no
`package.json`, Windows-first, `--json` / `--self-test` / `--prove-fail`, every finding carries
a citation.

Reuse rather than rewrite:

| Reuse from | What |
|---|---|
| `tools/extension-doctor.mjs` | `HOOK_EVENTS`, `KNOWN_TOOLS`, settings discovery across 4 scopes, `frontmatterProblems`, `runChecks` as the load gate |
| `tests/lint-bench/run-bench.mjs` | `hashTree`, `spawnTool`, `probeEnv`, the HOME/USERPROFILE redirection, and the "false positive weighted exactly like a miss" scoring rule |
| `references/hook-events.md` | the 30-event contract table, for exit-code and blocking semantics per event |

**Critical guard, learned the hard way in this repo:** add the `IS_MAIN` guard on day one.
`tier3-pack.mjs` carries a comment recording that without it, one tool's `--self-test` silently
ran a different file's self-test to completion and both reported PASS.

### The conformance spec: `conformance.json`

Sits beside `hooks.json`. Four case kinds, each mapping to a failure the GitHub corpus showed
is real:

```json
{
  "extension": "infra-guard",
  "mechanism": "hook",
  "cases": [
    { "id": "C1", "kind": "enforce", "event": "PreToolUse",
      "input": { "tool_name": "Write", "tool_input": { "file_path": "infra/main.tf" } },
      "expect": { "decision": "deny" } },

    { "id": "C2", "kind": "near-miss", "event": "PreToolUse",
      "input": { "tool_name": "Write", "tool_input": { "file_path": "src/app.ts" } },
      "expect": { "decision": { "not": "deny" } } },

    { "id": "C3", "kind": "wiring", "event": "PreToolUse",
      "input": { "tool_name": "Edit", "tool_input": { "file_path": "infra/main.tf" } },
      "expect": { "fired": { "min": 1 }, "decision": "deny" } },

    { "id": "C4", "kind": "fail-posture", "mutate": "delete-handler",
      "expect": { "decision": { "not": "allow" } } }
  ]
}
```

- **`enforce`** the thing it must block.
- **`near-miss`** the thing it must NOT block. A false positive is weighted exactly like a
  miss, the precedent already set in `run-bench.mjs`. This is the only defence against a
  deny-everything hook, and its coverage is bounded by the near-misses we thought of, which is
  a real limit not a solved problem.
- **`wiring`** the matcher actually selects this handler for this tool. **This is the case kind
  nothing in the ecosystem has.**
- **`fail-posture`** delete the handler, then make it exit non-zero. Assert the verdict does not
  become `allow`. This is the advisory-versus-enforceable finding made executable: users write
  prose and expect a guarantee, and a command hook fails OPEN.

### Scoring is structural, never textual

Cases are scored against a verdict object `{fired, decision, exit, stdoutJson, mutated}`, never
against a regex over run output. A handler that prints "BLOCKED: not permitted" to stdout with
exit 0 and no `hookSpecificOutput` must score MISS on every `enforce` case, and that exact case
is a self-test fixture. This is the structural version of the bench's existing
boilerplate-immunity rule.

### `--prove-fail` for the prover itself

Runs every case against two controls:

1. **empty**: the bare fixture tree, nothing installed.
2. **inert**: valid settings, handler present and executable, handler always `exit 0` with empty
   stdout.

Every `enforce` case must go RED against both. Empty catches "the case passes because of the
fixture". Inert catches "the case passes because a file exists". If any survives, print
**`PROVER IS HOLLOW`** and exit 1, mirroring `run-tests.mjs`'s existing `SUITE IS HOLLOW`.

## Phase 2: the creator wrapper

### New: `tools/extension-scaffold.mjs`

Composition, not competition. It does not reimplement `create-plugin`.

1. Take the requirement text and the mechanism chosen via the existing `references/selection.md`.
2. Emit (or delegate to `create-plugin` for) the bundle.
3. **Emit `conformance.json` derived from the requirement**, which is the part nobody does.
4. Run `extension-doctor.mjs` (static) then `extension-prove.mjs` (behavioural).
5. Report both, refusing to declare done while any `enforce` case is red.

### The guarantee-language guard

Grounded in measured GitHub behaviour (#17908, #56383, #80211, #16011): when the requirement
contains guarantee words (`always`, `never`, `must`, `block`, `prevent`, `ensure`), the scaffold
**must not** emit advisory CLAUDE.md prose as the primary mechanism. It emits an enforcing
mechanism and states why. It must also always consider a `permissions.deny` rule, because in
every one of those issues the deny rule went unconsidered.

### Reference update

Extend the existing `skills/claude-code-extension-engineering/references/testing.md` rather than
adding a new file. It already covers "control run, trigger versus behaviour tests, regression
strategy" and is the natural home for the conformance-spec contract.

## Phase 3: the measured demonstration

### New: `tests/prove-bench/`

Roughly 10 items, same fixture-tree shape as the existing 15 in `tests/lint-bench/fixtures/`, so
the isolation machinery transfers unchanged. Each item is a hook that is **deliberately wrong in
one specific way**: allows what it should block, matcher scoped to the wrong tool, fails open on
crash, blocks the near-miss.

Every item is scored against **both** `test-hook.sh` and `extension-prove.mjs`. The expected
table is the product claim, in the same shape as `tests/results-lint-bench.md`.

**Two controls that stop this being self-certifying:**

1. A **correct** hook that both tools must pass. Without it we have built a check that cannot
   fail, which is precisely the defect we are calling out in `test-hook.sh`.
2. Every item's defect is stated in its manifest with the citation for why it is a defect, so a
   reader can dispute the item rather than trust the score.

Honest limit to publish alongside: we author both the fixtures and the expected outcomes, which
is the same construct-validity weakness `tests/results-lint-bench.md` already discloses about
its own 12 of 12. The bench is a demonstration, not proof of a general capability.

## Verification

Ordered so the cheapest kill-shot runs first.

1. **The prover can fail.** `node tools/extension-prove.mjs --prove-fail` against the empty and
   inert bundles. Every `enforce` case must go RED. If anything survives, stop: the prover is
   asserting nothing.
2. **The prover is clean on a correct extension.** Zero failures on the control item. A prover
   that flags a correct hook is worse than none.
3. **The differentiator reproduces.** On the same deliberately-wrong hook:
   ```bash
   bash "$PLUGIN_DEV/skills/hook-development/scripts/test-hook.sh" handler.sh input.json; echo "exit=$?"
   node tools/extension-prove.mjs --bundle tests/prove-bench/fixtures/allows-what-it-blocks; echo "exit=$?"
   ```
   Expect `test-hook.sh` exit 0 with a success banner, `extension-prove.mjs` exit 1 naming the
   case. If this does not reproduce, the entire premise is wrong and the plan stops here.
4. **Self-tests and drift gates.** `--self-test` on prove and prove-bench; `--check` on the
   fixture generator.
5. **No regression.** The full existing bar: `node tests/run-tests.mjs`,
   `node tests/run-tests.mjs --prove-fail`, `node tools/verify-evidence.mjs`,
   `node tools/extension-doctor.mjs --self-test`, `node tests/lint-bench/run-bench.mjs --self-test`,
   plus every tier3 self-test and `--check`.
6. **Independent review.** Per the house rule, a separate agent executes a neutral
   `_verify.md` spec and writes the evidence-backed `_review.md`. Author self-review is not
   accepted, and this plan is no exception.

## Risks, ranked

1. **The prover becomes a simulator we grade ourselves against.** We would be asserting
   conformance to *our reading* of `hooks.md`, not to Claude Code. Bounded by keeping Phase 1
   to hook mechanics that are stated verbatim in the docs with a citation per case kind, and by
   deferring anything ambiguous. If Tier 4 is ever built, simulator fidelity against live
   sessions becomes a hard go/no-go gate, not an afterthought.
2. **Fixtures we author, expected outcomes we author.** Same construct-validity limit already
   disclosed for the lint bench. Mitigated by the correct-hook control and per-item citations,
   not eliminated.
3. **Adoption.** The buyer is someone who ran `create-plugin` and believes they are covered
   because `plugin-validator` printed PASS. We are selling a fix for a problem they do not know
   they have. The one-command demo is the only honest marketing.
4. **The upstream fixes land and the gap closes.** Four one-line fixes would remove much of the
   differentiator. That is a good outcome for the ecosystem and a real risk to the product. It
   is a reason to file them and to lead with the wiring check, which is the piece with no
   incumbent at all.
5. **Scope creep back into a full generator.** Phase 2 must stay a wrapper. The moment it
   reimplements `create-plugin`, we are duplicating working code and the null-refuted "more
   content" strategy returns through the back door.
